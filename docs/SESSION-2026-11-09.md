## Что починено по дороге

### Write-тесты

1. `mkdir("/tmp/t")` падал с `EEXIST` — том данных persistent, `/tmp/t` остался с прошлого прогона.
   `test_writable` теперь при `EEXIST` убирает свои старые имена (`sweep_test_dir`) и идёт дальше.
2. **Hard link.** `apfs_vnop_remove` звал `apfs_node_refresh(am, vp)` вместо
   `apfs_node_refresh(am, APFS_VP(vp))`: vnode читался как `struct apfs_node`, refresh читал мусор
   (`an_id` = `0xDEADB`) и писал `an_ino` в чужую память. Второй баг: флаг `an_unlinked` ставился
   на промежуточном unlink — теперь только когда ушло последнее имя (`an_ino.nchildren <= 1`).
3. **Удаление последнего имени открытого файла — отложенное.** `fs_remove_file` получил флаг
   `keep`: `nchildren = 0`, запись каталога уходит, инод/экстенты/xattr'ы остаются; `VNOP_INACTIVE`
   на последнем close зовёт `apfs_delete_inode` (`op_orphan_delete`). `va_nlink` = 0.
4. **Сокет.** Не было `VNOP_MKNOD` — bind AF_UNIX отбивался `EPERM`. Добавлен `apfs_vnop_mknod`
   для `VSOCK`/`VFIFO`; тип берётся из `va_type`, а не из `va_mode`.
5. **Graft `/var/jb`** терпит `EEXIST` на persistent-томе (первый раз ~8 мин, ~7000 транзакций).
6. Те 4 «чтения system image» оказались отсутствующими `share/pattern.bin` и `bin/child` в
   payload-образе — вернул (формула из `build.sh`, `child` собран `xnu-clang` + libmini).

### dyld / launchd

- **Полный лог ядра:** `oem log` пересобирает staged-буфер из одного loader-лога; после возврата
  ядра `write_logs()` уже положил туда весь лог — `get_staged` **без** `oem log` отдаёт 170 КБ
  (было 32 КБ) с хвостом, паникой и стекшотом.
- **Паника:** `EXC_RESOURCE -> launchd.ios[1] exceeded mem limit: ActiveHard 50 MB (fatal)` →
  `memorystatus: killing process 1` → `panic: initproc exited` (namespace 1 subcode 0x7).
  Причина — `DYLD_SHARED_REGION=private` (dyld мапит 2.6 ГБ кэша в процесс).
- **Правка:** убраны `DYLD_SHARED_REGION` и `DYLD_SHARED_CACHE_DIR` из окружения `exec` в
  `userland/src/init.c`; остался `DYLD_PRINT_TO_FILE=/private/var/dyld.log`. dyld берёт кэш по
  дефолтному пути `/System/Cryptexes/OS/System/Library/Caches/com.apple.dyld/` и shared-регион ядра.
- **Результат:** ядро не падает; launchd: `Darwin Bootstrapper Version 7.0.0`,
  `Restore environment starting`, `Early boot complete. Continuing system boot.`, домен `user/501`,
  демо-джоб `com.hakios.demo` спавнится (pid 4) и выходит `exit(0)`.

## Где остановились

launchd сидит в **restore**-режиме: `rd=md0` + boot spec «ramdisk», boot tasks скипаются,
SpringBoard/backboardd не стартуют. В образе нет `/System/Library/xpc/launchd.plist` (в payload-дереве
нет `xpc/`) — `launchd_cache_loader` скипается, не критично.

Вопросы на следующую сессию:

1. Как вывести launchd в обычный boot mode (без restore): boot-args, boot-mode NVRAM, ignition
   (`skipIgnition`) или подготовка образа.
2. Нужен ли свой маунт Cryptex: в подготовленном образе кэш лежит прямо в
   `/System/Cryptexes/OS/System/Library/Caches/com.apple.dyld`, cryptex не монтируется; хватает ли
   этого для SpringBoard.
3. Положить `xpc/` в payload-дерево (launchd.plist + cache) — уберёт «Unable to load cache».

## Вечер-3: lsd — не exit(78); хост-нагрузка; паника стека; первый сбой на чистом томе

### lsd

`exit(78)` — это `xpcproxy`: он не смог `posix_spawn(/usr/libexec/lsd)` (ENOENT в XNU — либо
файла нет, либо не нашёлся `/usr/lib/dyld`). Проверено джобами в одном прогоне:

| джоба | программа | результат |
|---|---|---|
| `com.hakios.lsd1` | `/usr/libexec/lsd`, mobile | `posix_spawn ... 0x2` (на свежем томе) |
| `com.hakios.lsd3` | `/usr/bin/vm_stat`, тот же plist | стартует |
| `com.hakios.lsd4` | те же байты в рамдиске (`/redwood/bin/lsd-copy`) | стартует |
| `com.hakios.lsd7` | `/usr/libexec/lsd`, **root** | стартует |
| `com.hakios.lsd8` | `/usr/libexec/nehelper` | стартует |

Проба из `init` (`lau_probe`): `open /usr/libexec/lsd` → fd 3, `read 32` → `cf fa ed fe`,
`execve` из дочернего — **без ошибки**. То есть файл, том и VFS в порядке. На уже графтнутом
томе lsd стартует и через xpcproxy. Вывод: ENOENT — **состояние системы**, а не свойство пути
(скорее всего тот же сбой, что ниже: чтение/page-in, отдающий отказ).

Отдельно: в `phone9boot` и позже lsd падает уже **SIGABRT** — это исходный nil в NSURL
(`pathProviderForSystemContainerForCurrentProcess`). Из `etc/inject.conf` в `mk11.sh`/`mk13.sh`
lsd убрали, поэтому обход nil в нём сейчас не работает. Вернуть строку
`/redwood/lib/libhakios.dylib … lsd`.

### Теги освобождений и паника

`txn_free` теперь знает вызывающего: `a tree node` (oid), `a file extent` (sid), `the tail of a
truncated file` (sid), `an inode's extents` (ino), `the commit retiring an old object` (0..8).
Сообщения: «given back twice in one transaction: X, then Y», «given back but was free already:
X asked for it», «cannot be given back: X».

**Паника `Invalid kernel stack pointer`** (прогон `phone13boot`, упал accountsd): кадры
повторяют `btp_update_node+0x490` → `+0x90` — рекурсия в себя. Предел был `depth > 16`, кадр
большой, 16 КБ стека не хватало. Теперь `BTP_MAX_DEPTH 6` и лог `tree too deep at block N (level D)`.

**UFS-лог.** Успешные строки переключения списка контроллера писались на каждый блок коммита
(885 КБ за прогон, мусор на экране) — теперь они под `ufs_trace=1`; в логе осталось 4 строки
вместо 323.

### Чистый том (seed + boot, 10 минут, без паники)

SpringBoard, backboardd и lsd стартуют (lsd — с SIGABRT по nil). Через ~5,5 минут сессии — первый
сбой записи:

```
apfs: create com.apple.celestial.plist: inode 9778, no vnode: 5
apfs: fs: operation refused: 5
```

То есть файл создан и закоммичен, а `apfs_node_vnode` не смог сделать vnode (EIO), и create
откатывается unlink'ом. Дальше по нарастающей: 530 `apfs: fs:` за сессию, затем

```
apfs: block 30365 is given back but was free already: the commit retiring an old object 0x6 asked for it
apfs: block 30346 is given back twice in one transaction: a tree node 0x768a, then the commit retiring an old object 0x8
apfs: fs: commit failed: 5
```

Похоже на каскад: `fs_commit` ставит `nx->omap_addr = nx_obj_addr` **до** `apfs_txn_commit`; если
коммит не удался, следующий коммит освобождает блок, который так и не был опубликован. Но первый
сбой — «no vnode» после успешного create, и его ещё надо назвать: смотреть `apfs_node_vnode` →
`apfs_inode_get` (какой код и из какого места отдаёт EIO) и проверять, что корень fs-дерева,
записанный в суперблок, действительно ведёт к только что вставленной иноде.

### Что дальше (по порядку)

1. Вернуть lsd в `etc/inject.conf` (обход nil) — иначе он падает SIGABRT.
2. Назвать первый EIO: лог в `apfs_node_vnode`/`apfs_inode_get` (какой именно вызов).
3. При неудачном `apfs_txn_commit` откатывать `nx->omap_addr` (и вообще все поля, которые

4. После этого — SIGBUS-шторм (54 за прогон) и первый кадр SpringBoard.
5. Hard link: sibling-записи в приватном каталоге (apfsck `wrong name for only link`).

#### 3. Причина lsd exit(78)
В логе p73 xpcproxy завершается с exit(78) из-за:
posix_spawn(/usr/libexec/lsd), error 0x2 - No such file or directory.
Причина локализована:
- Джоба под oot запускается успешно (com.hakios.lsd7).
- Джоба под mobile падает с ENOENT, потому что entitlement com.apple.security.system-container заставляет xpcproxy вызывать _sandbox_spawnattrs_setcontainer. На чистом томе без готового каталога /private/var/containers/Data/System/com.apple.lsd ядро/песочница возвращает ENOENT (0x2).
- При обходе sandbox/контейнера или запуске под root lsd стартует и переходит к созданию базы LaunchServices, где далее требуется перехват nil в NSURL (уже реализован в libhakios.dylib).

#### 4. Следующие шаги
1. Добавить перехватчик watch_for_faults в inject_sb.c (libhakios.sb.dylib), чтобы получить точный стек и причину SIGBUS в SpringBoard.
2. Зафиксировать запуск lsd (создание контейнера в skel либо запуск от root).
